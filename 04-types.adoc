= 型解析

ここまで見てきたようなGoの抽象構文木を扱うAPIを知っていれば、Goプログラムの静的な操作はある程度できるようになったと言っていいでしょう。しかし、より深く、

* ソースコード中に登場する名前が定義された位置や、
* ある型がインタフェースを実装しているか

など、プログラムの構造を越えたより高度な情報が必要になった場合は、**型解析**に手を出す必要があります。

この章では、Goパッケージの型チェックと型にまつわるデータ構造を提供する `go/types` パッケージのAPIを見ていきます。

== 型チェックを行う

`types` パッケージによる型チェックは、`types.Config` 構造体の `Check` メソッドを呼ぶところから始まります。

`files []ast.File` には、ひとつのパッケージを構成する構文解析されたファイル群を指定します。<<ファイルの構文解析>> で `files` の要素を生成した際に使用した `fset` も引数として渡します。

最後の引数である `info *types.Info` は、パッケージ内の型にまつわる詳細な情報を格納する先として指定します。単純に型チェックを行いたいだけの場合は `nil` でも構いません。

このように、型チェックおよび型情報の取得は `Config` 構造体をエントリポイントとしてパッケージごとに行います。結果は <<types.Package>> 構造体と、ここでは登場しませんでしたが <<types.Info>> 構造体に格納されます。

== types.Config

`types.Config` 構造体が `go/types` パッケージのエントリポイントとなります。

godoc::go/types.Config[]

各フィールドを調整することで、`Check()` による型チェックを行う際の挙動をカスタマイズできます。

特に、`Error func(err error)` は型チェックの際に生じたエラーを全て受け取るコールバックとして便利です。これが `nil` である場合、最初のエラーが起きた時点で型チェックが停止します。

== パッケージのインポート

`types.Config.Importer` は、`types.Importer` という型を持つフィールドです。プログラムの型チェックを行うためにはインポートしているパッケージがどんな名前と型を提供するのか知る必要があるため、`Config` 構造体の `Importer` フィールドという形でその実装を指定します。

godoc::go/types.Importer[]

`types.Importer` は、パッケージのパスを解決し、そのパッケージに関する型レベルの情報を返すインタフェースです。

=== go/importer

この具体的な実装を提供していたが `go/importer` パッケージ**でした**。

でした、というのは、このパッケージはlink:++https://pkg.go.dev/cmd/go#hdr-Modules__module_versions__and_more++[Go modules]のリリース前につくられたもので、現在の標準的なモジュール管理方法であるGo modulesに対応していないためです。

このモジュールは非推奨とはなっていないものの、上記の理由により、外部のモジュールに依存するようなプログラムに対しては使うべきではないとされています。

インポートの解決に限らず、型解析には `golang.org/x/tools/go/packages` パッケージの利用が推奨されますが、ここで少々 `go/importer` について触れておきます。

== 型チェックのエラー

型チェック時のエラーは `types.Error` 構造体によって表現されます。

godoc::go/types.Error[]

エラーの起きた位置情報に加え、`Soft` フィールドを持っています。このフィールドは、当該のエラーが「ソフト」であるかどうかを示します。ソフトなエラーは、型チェックそのものには影響を与えません。具体的には、以下のエラーです。

* `import` されたパッケージが使用されていない
* 定義された変数が使用されていない
* ラベルが利用されていない・重複している
* `goto` がジャンプ先までの間の変数宣言を飛び越えている
* `:=` の左辺に新しい変数が登場していない
* `init` 関数の本体が存在しない
* 型パラメータを持つ関数の本体が存在しない
// 関数の本体については https://go.dev/ref/spec#Function_declarations
* `init` 関数や `main` パッケージの `main` 関数が型パラメータ・引数・戻り値を持っている
* C形式の `for` 文の後処理文で変数を定義しようとしている +
  …… `for i := 0; i < 10; i, j := i+1, i {` のような形。構文解析の時点では受けつけてしまいます
// parseSimpleStmt。spec でも "PostStmt = SimpleStmt ." となってる

* 最後のパラメータ以外で可変長引数の `...` を使っている
* 型引数が型パラメータの制約を満たしていない
* 型制約でしか使えないインタフェース（`comparable` や型の集合を含むもの）を通常の型として使っている
* 型制約の和が重複している（`~int | ~int` など）

== スコープ

`types.Package` 構造体において `Path` や `Name` などの基本的な情報の他に有用なのは、解析されたパッケージのスコープ情報でしょう。

Goのソースコードに登場する名前はレキシカルスコープを持ち、その有効範囲は静的に決まります。型チェックの過程では、このスコープにしたがって、ソースコード中の識別子がどの宣言に由来するものであるかを解決します。

=== スコープを形成するブロック

Goのスコープはブロックにもとづいて作られます。ブレース（`{ ... }`）による明示的なブロックのほかにも、暗黙に作られるブロックがあります。link:https://go.dev/ref/spec#Blocks[Blocks]およびlink:https://go.dev/ref/spec#Declarations_and_scope[Declarations and scope - The Go Programming Language Specification]に述べられていますが、重要な部分を抄訳します：

* 暗黙のユニバースブロック（universe block）は、すべてのソースコードを含みます。あらかじめ宣言された名前（`int` や `nil`、`len` など）はここに属します。
* パッケージは暗黙のパッケージブロック（package block）を持ち、パッケージを構成するすべてのソースコードを含みます。トップレベルに宣言された定数、型、変数、関数（メソッドを除く）の名前はここに属します。
* ファイルは暗黙のファイルブロック（file block）を持ち、ひとつのファイルのソースコードを含みます。インポートされたパッケージの名前はここに属します。
* `if`、`for`、`switch` 文はそれ自身が暗黙のブロックを作ります。`switch` や `select` の各節（case）も同様です。

=== types.Scope

== オブジェクト

`go/types` では、名前解決によって識別子（`ast.Ident`）と対応づけられたシンボルまたはterm:名前をつけられた言語上の要素[named language entity]をterm:オブジェクト[object]と呼んでいます。このオブジェクトは名前や型、その実体の情報を持ちます。<<スコープ>>が名前から引くのはこのオブジェクトです。

オブジェクトは `types.Object` インタフェースとして表現されています。

godoc::go/types.Object[]

`Name()` や `Pos()` でオブジェクトの名前や宣言された位置を、`Type()` でその型を、`Parent()` でそのオブジェクトが宣言されたスコープを得られます。

オブジェクトの種類は `types.Object` を実装する具体的なデータ型によって区別されます。`types` パッケージで表現されるオブジェクトの種類と、対応するデータ型は以下のようになっています。

* 組み込み関数（`*types.Builtin`）
* 定数（`*types.Const`）
* 関数（`*types.Func`）
* ラベル（`*types.Label`）
* `nil` （`*types.Nil`）
* インポートされたパッケージ（`*types.PkgName`）
* 宣言された型（`*types.TypeName`）
* 宣言された変数など（`*types.Var`）
// ^ などってのは struct field も含むから

これらについて、以下で見ていきます。

=== types.Func

関数を表します。より詳細には、

- 宣言された関数
- 具象メソッド
- （インタフェースの）抽象メソッド

です。

以下で、それぞれの場合（トップレベルの関数 `F`、型 `*T` のメソッド `F`、インタフェース `I` のメソッド `F`）の出現を確認しています。

goexample::typesfunc[]

goexample::typesfunc[output]

<1> パッケージスコープ内の名前にアクセスします。`F` はトップレベルの関数に、`T` および `I` は型名に対応するオブジェクトとして取得します。
<2> 型 `T` に属する最初のメソッドとして、`T.F()` に対応するオブジェクトを取得します。
<3> 型 `I` が指すインタフェース `interface { F() }` の最初の（抽象）メソッドとして、`I.F()` に対応するオブジェクトを取得します。

このように、インタフェースの抽象メソッドと、それ以外の具象メソッドに対応するオブジェクトへアクセスする方法は微妙に異なります。

関数やメソッドの持つ型は、`types.Signature` として表現され、これが関数のレシーバ・パラメータや戻り値、型パラメータなどの情報を保持します。

型パラメータを持つ関数（`func F[T any](x T)`）や、ジェネリックな型のメソッド（`func (Gen[T]) Meth(argT T)`）も `Func` として表現されます。また、ジェネリックな型のインスタンス化にともなって合成される `Func` もあります。これらについては<<ジェネリクス>>で詳しく扱います。

=== types.TypeName

名前をつけられた型を表します。具体的には、以下のいずれかに対応します。

* 定義された型（`types.Named`）… `type T struct{}` など
* 型エイリアス（`types.Alias`）… `type A = T` など
* 型パラメータ（`types.TypeParam`）… `func F[P any]()` の `P`
* あらかじめ宣言された型 … `int` や `error` など

`TypeName` が表す型は、`Type()` メソッドで得られる `types.Type` になります。以下のサンプルコードで、「あらかじめ宣言された型」がそれぞれどのように表現されているか確認します。

goexample::typesuniversetypename[]
goexample::typesuniversetypename[output]

* `any` は `interface{}` のエイリアスです。
* `comparable` は `interface{ comparable }` に名前をつけたもの、という扱いです。循環参照みたいですが、参照先は「内部的にcomparableフラグが立っている」ようなインタフェースとして表現されています。

* `byte` と `rune` はエイリアスだとみなされますが、その表現は `types.Basic` です。実際、それぞれ `uint8` と `int32` と同じ属性を持ち、別の名前を持つ型として表現されています。

=== types.Type

==== Underlying type

`Underlying()` メソッドは、その型のlink:https://go.dev/ref/spec#Underlying_types[Underlying type]を返します。仕様上、すべての型はunderlying typeを持ち、

[loweralpha]
. あらかじめ宣言された型や、型リテラルで書かれた型のunderlying typeは、その型自身
. `type T ...` のように宣言された型 `T` のunderlying typeは、その参照する先の型のunderlying type
. 型パラメータのunderlying typeは、その制約のunderlying type（つまりインタフェース型）

です。この定義を辿れば、underlying typeはa.のあらかじめ宣言された型もしくは型リテラルで書かれた型になります。

なので、ある型についてその詳細（構造体型のフィールドなど）を知りたいときは、一度 `Underlying()` を経由して確認することになります。

[source,go]
----
if st, ok := typ.Underlying().(*types.Struct); ok {
	// ...
}
----

=== types.Named

`types.Named` は、`type T struct{ ... }` のような型宣言によって定義された型（link:https://go.dev/ref/spec#Type_definitions[defined types]）を表します。

godoc::go/types.Named[]

[NOTE]
.Named = Defined?
====
Go 1.9で型エイリアスが導入される以前、仕様では型定義によって作られる型のことを「named type」と呼んでいました。当時は型に名前をつける方法が型定義のみだったので、名前を持つ型はつねにほかの型と異なる固有の型だったからです。

型エイリアスの登場によって、名前を持つにもかかわらず別の型と同一である型が存在するようになったため、型定義によって作られる型のことを「defined type」と呼ぶようになりました。

`go/types` の `types.Named` は以前のこの呼び方を引き継いだものです。

ちなみに、現在の仕様では、「named type」は `any` を除くterm:事前宣言された型[predeclared types]、defined type、型パラメータを指すことになっています（link:https://go.dev/ref/spec#Types[Types]）。`any` が除かれているのは、これが型リテラル `interface{}` のエイリアスだからです。

// https://go-review.googlesource.com/c/go/+/36213
// 変更前の仕様（「Two named types are identical if their type names originate in the same TypeSpec」）:
// https://github.com/golang/go/blob/go1.8/doc/go_spec.html#L1421
// Go 1.18 で named type が「固有の同一性を持つ型」の総称として再導入された経緯は、以下のコミットメッセージにまとまっている:
// https://go-review.googlesource.com/c/go/+/757120
====

その名のとおり名前を持っているので、 `Obj()` メソッドによりその型を宣言した<<types.TypeName>>オブジェクトを得られます。

==== ジェネリックな型

ジェネリックな型の宣言 `type List[T any] []T` も `types.Named` で表現され、`TypeParams()` でその型パラメータの一覧を得られます。

また、`List[string]` のようにインスタンス化された型も、それぞれ別の `types.Named` として表現されます。インスタンスに対しては `TypeArgs()` で型引数の一覧を、`Origin()` でインスタンス化の元になったジェネリックな型を得られます。これについては<<ジェネリクス>>で詳しく扱います。

=== types.Signature

`types.Signature` は関数の型を表します。宣言された関数やメソッド、関数リテラルが持つ型です。

=== オブジェクトのインスタンス化

ジェネリックな型や関数の型パラメータを型引数で置き換えることをインスタンス化と呼びます（link:https://go.dev/ref/spec#Instantiations[Instantiations]）。

`go/types` では、このようにしてインスタンス化された宣言を、合成されたオブジェクトとして表します。

たとえば以下のプログラムにおいて、`g.FieldT` と `h.FieldT` はどちらも `Gen` の宣言中の `FieldT T` に由来しますが、型はそれぞれ `int` と `string` であり、それぞれ別の `Var` オブジェクトが対応します。一方で `g.FieldNum` と `h.FieldNum` は同一のオブジェクトです。

[source,go]
----
package p

type Gen[T any] struct {
	FieldT   T
	FieldNum int
}

var g Gen[int]
var h Gen[string]

var _ = g.FieldT
var _ = h.FieldT
var _ = g.FieldNum
var _ = h.FieldNum
----

このような合成されたオブジェクトはその `Pos()` が元のジェネリックなオブジェクトの位置と同一であり、`Origin()` メソッドで、元のオブジェクトを得られます。

godoc::go/types.Var.Origin[]

godoc::go/types.Func.Origin[]

合成されるのは、以下のオブジェクトです。

* ジェネリックな型をインスタンス化したとき
** その型パラメータに依存するフィールド `types.Var`
** そのメソッド `types.Func` と、そのレシーバ・パラメータ・戻り値 `types.Var`
** そのメソッドがジェネリックである場合は、その型パラメータ `types.TypeName`
* ジェネリックな関数やメソッドをインスタンス化したとき
** パラメータ・戻り値 `types.Var`

NOTE: 合成されたオブジェクトは基本的に `Origin()` メソッドで元のオブジェクトを参照できますが、執筆時点（Go 1.27）では、ジェネリックなメソッドの型パラメータには `Origin()` が存在しないようです。
